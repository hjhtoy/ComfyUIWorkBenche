## 任务队列增加排序

- 诉求：队列无法排序，需要按名称、视频时长、耗时排序。
- 实现（队列是卡片列表，无表头，用工具栏下拉）：
  - `page.html`：`#queueTools` 最前加 `#queueSort` 下拉，7 个选项：最新优先（默认）/ 名称 A→Z / 名称 Z→A / 视频时长 短→长 / 长→短 / 耗时 短→长 / 长→短。
  - `queue-view.js`：`sortValue()` + `orderedJobs()` + `applyQueueOrder()`；`render()` 末尾调用重排（先比较 DOM 顺序，一致则不动，避免频繁重排）；`#queueSort` change 时 `writeLocal('frameform.queue-sort.v1')` 持久化，初始化读取并回填 select。
  - 排序规则：名称用 `localeCompare(..., 'zh-Hans-CN', {numeric:true})`；时长取 `j.duration`（秒）；耗时取 `endedAt - startedAt`，**未结束任务没有耗时，排最后**（升降序都排最后）；缺值兜底按任务号降序，保证稳定。
  - 任务编号 `n` 不随排序改变（编号是任务序号，排序只影响显示顺序）。
  - `base.css`：`.queue-sort select` 样式（复用按钮配色）。
- 测试：`test_queue_tabs.py` 的 fixture 增加 `duration` 与 `startedAt/endedAt`，断言时长升降序、耗时升降序（未完成任务在末尾）、名称升降序互逆、localStorage 持久化、末尾 reload 后顺序一致。
- 坑：`persist()` 只保留 `sent || terminal` 的任务，测试中间 reload 会丢掉"排队中未发送"的任务（既有行为，非本次引入）；因此刷新验证放到测试末尾，并只校验保留任务的相对顺序。
- 全量回归 22/22 通过。前端是单 HTML 内联产物，服务端每次请求重新读文件，刷新即可生效，无需重启。

## 修复：服务重启后进行中任务显示连接报错

- 现象：ComfyUI（127.0.0.1:7860）重启/短暂不可达时，Worker 把 `工作区将重试：Cannot connect ...` 写进**每个任务**的 `warn`，前端在任务卡片上显示成报错；且队列/历史都查不到的任务会永久轮询"等待确认"。
- 修复（`workspace/worker.py`）：
  - 新增 `Worker.connection`；`follow()` 把 `ClientError/TimeoutError/OSError` 归为连接问题，只写全局提示、**不再写任务 warn**；仅 `ValueError`（数据问题）保留任务级 warn。
  - `run()` 启动时用一次 SQL 清理历史遗留的 `warn LIKE '%Cannot connect%'`；无进行中任务时清空 `connection`。
  - `poll()` 中队列与历史都找不到时累计 `absent`，连续 3 次 → `lost`，note="ComfyUI 已重启或队列已清空，无法确认任务最终状态"（不再无限等待）。
  - 连接恢复后 poll 成功自动清空 `connection` 并刷新 state/排队位置。
- `workspace/server.py`：`/workspace/jobs?since=` 响应增加 `connection` 字段；`src/jobs/workspace-runner.js` 把它显示在 `#queueSync`（一条全局提示，不占任务卡片）。
- 测试：新增 `tests/test_worker_recovery.py`（无需浏览器）：任务消失→lost；503→只设全局提示、任务无 warn；恢复→提示清空且状态变 running。全量 23/23 通过。
- 实测：重启服务后 61 个进行中任务 warn 全部为空，ComfyUI 恢复后状态自动刷新。
- 注意：ComfyUI 真重启且队列清空时，任务会变"已停止跟踪"（结果确实丢了），需要重新提交；若历史仍在则直接恢复为已完成。

## 修复：H3「视频模型做图片编辑」工作流参数区为空

- 现象：导入 `H3 视频模型做图片编辑.json` 后，参数设置区块什么都没有。
- 根因（`src/library/mapping.js`）：
  - 提示词链路是 `160 CR Text → CR Text Replace.replace1 → 272.text → 239 QwenVL.custom_prompt → 178.prompt`；旧 `promptSource` 只认原生 `StringReplace`（`find/replace`），不认 Comfyroll 的 `CR Text Replace`（`find1..3/replace1..3`），所以 `profile.prompt` 为空。
  - 步数：`16 SamplerCustomAdvanced.sigmas → 195 ExtendIntermediateSigmas.sigmas → 14 BasicScheduler.steps`；`samplingConfig` 只处理 sigmas 直达 BasicScheduler，中间隔一个节点就断了。
  - 尺寸：`178.width/height ← 191 easy imageSize ← 146 ImageScaleToTotalPixels`，尺寸由输入底图动态计算，**没有固定宽高字段**，所以没有尺寸控件（工作流设计，不是 bug）。
- 修复：
  - `promptSource` 增加 `CR[ _]Text[ _]Replace` 分支：find1..3 非空时取 replace 指向的文本节点（`text/value/string/prompt`）。
  - `samplingConfig` 增加 `ExtendIntermediateSigmas` 穿透到 `BasicScheduler.steps`。
  - `mappingVersion` 3 → 4；`repairSavedMapping` 的 steps 补全去掉 HyperFlowSigmas 限制（仍用 available 防覆盖）。已保存条目打开工作流库时自动修复并写回。
  - `composer.js`：有素材槽位时，若默认提示词**不含** `<Picture|Video|Audio N>` 标签则预填（原先完全不预填）。
- 测试：新增 fixture `tests/fixtures/h3-reference-edit.api.json`；`test_h3_prompt_chain.py` 增加第三段：导入断言 `#workflowPrompt == ["160","text"]`、步数 8、默认文本预填、两张不同图片素材、提交后 `160.text` 写入新指令且 `241` 模板不变、`14.steps` 写入 12。全量 23/23 通过。

## 诊断：RunningHub `/proxy` 无法提交任务

- 现象：配置 `https://www.runninghub.cn/proxy/<key>`，连接测试通过，提交后任务 3 秒变 lost（`id=None`）。
- 实测（用户真实 base）：
  - `GET /system_stats` 200（真实实例：4090 24G / ComfyUI 0.3.27）；
  - `GET /queue` 200 空；`GET /history?max_items=1` 200，只有一条旧记录；
  - `POST /prompt` 对无效节点、空图、带 `Authorization: Bearer` 均返回 **200 `{}`**（非标准 `{prompt_id, number, node_errors}`）；
  - 提交 64×64 `EmptyImage + SaveImage` 零成本图后，`/queue` 仍空、`/history` 无新记录 → **任务未执行**。
  - `/prompt/`（尾斜杠）返回 404，说明路由精确存在。
- 结论：`/proxy` 读接口可用，写接口未真正接收（可能需平台侧活动实例/专属实例，或消费级 Key 不开放 `/proxy` 写）。项目无法从客户端修复。
- 顺带修复 Worker 的误判（`workspace/worker.py`）：
  - `submit` 不再用 `reply["prompt_id"]` 硬取，兼容 `{}`/`taskId`；无 id 也进入 `queued`，note="已提交，等待服务器确认"，并写 `submittedAt`。
  - 未确认任务（无 id）有 3 分钟宽限期，不再 3 秒判 lost；`/queue` 行结构容错（`.get`、长度/字典检查）。
  - `follow` 的 `except KeyError` 只在任务确实不存在时退出，其他 KeyError 重试。
- 测试：`test_worker_recovery.py` 增加"`/prompt` 返回 `{}` 仍保持 queued"场景；全量 23/23。
- 待用户确认：Key 类型、是否现在实现开放 API（`/task/openapi/create` + `/status` + `/outputs`，需要平台 workflowId）。
